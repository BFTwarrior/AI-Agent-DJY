# 02 维护手册

## 日常只需要一条命令

```bash
python tools/doctor.py
```

检查项：脚本齐全、解释器存在、`hooks.enabled`、三处钩子（`PostToolUse` 主 + `PostToolUseFailure` 兜底 + `SessionStart`；前两处要求 `matcher == "Bash"`，三处都要求脚本路径真实存在）、provider 指向、代理端口、**代理运行参数是否与当前脚本一致**、日志尾巴。有 FAIL 就按提示的路径处理，其余不用管。

其中「代理运行参数」专门抓“改完代码忘了重启代理”这个坑：它把 `proxy.log` 最后一条启动行里的 `retry <N>s window` / `every Ns` / `silence=Ns` / `heartbeat>=Ns` 四项，与脚本源码里的默认值逐一对照，任一项不一致就 WARN。

---

## 想调整错误处理

v0.4.0 起**没有错误类型分类**：任何失败的 Bash 调用都会建议重试，上限 3 次（第 4 次失败不再建议）。这是用户的明确规格，不要加回 FATAL 过滤。

唯一保留的模式表是 `UPSTREAM_PATTERNS`（`src/retry_hook.py` 顶部）：命中后建议先 `sleep 180` 等 3 分钟再发，因为这类“上游没产出”的错误立刻重发基本还是失败。要扩充就只往这一个列表里加。

规则是 Python 正则，不区分大小写。改完必须：

1. 手动喂一个样本来验证（见下方"本地验证"）
2. 更新 `CHANGELOG.md`
3. 重跑 `python tools/install.py` 覆盖已安装的脚本

**注意**：只有 `UPSTREAM_PATTERNS` 会影响措辞（等 3 分钟），不会影响“要不要重试”——任何失败都会重试，这个行为不该被模式表左右。

## 本地验证（不装也能测）

钩子脚本从 stdin 读 JSON，所以可以直接喂样本：

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"curl x"},"error":"operation timed out"}' \
  | python src/retry_hook.py
```

- 有输出 = 判定为可重试
- 无输出 = 放行

想隔离计数，加环境变量：

```bash
ZCODE_RETRY_HOOK_STATE_DIR=/tmp/rh-test python src/retry_hook.py < sample.json
```

**回归必须覆盖的四类样本**

| 样本 | 期望 |
|---|---|
| `operation timed out` | 有输出，不含 sleep |
| `upstream_deadline` | 有输出，含 sleep 180 |
| `permission denied` | **有输出**（v0.4.0 起不筛除类型） |
| 同命令连续 4 次 | 前 3 次有输出，第 4 次无输出 |

## 想加一个新的上游中转

1. 改 `src/retry_proxy.py` 的 `UPSTREAMS`：

   ```python
   UPSTREAMS = {
       "/ap": ("upstream-a.example.com", 443),
       "/cm": ("upstream-b.example.com", 443),
       "/xx": ("新域名", 443),          # 新增
   }
   ```

2. 在 `tools/install.py` 的 `PREFIXES` 字典里加对应条目（键是前缀名，值是完整 baseUrl），前缀名会自动成为 `--proxy-prefix` 的合法取值。
3. 重启代理（见下）。

## 可调参数（环境变量）

代理的所有节奏都能用环境变量覆盖，改完重启生效：

| 变量 | 默认 | 含义 |
|---|---|---|
| `PROXY_RETRY_WINDOW` | `180` | 持续重试的时间窗（秒）。到点后不再发起新尝试；已在飞的那一次允许跑完，所以实际耗时可能略超窗口 |
| `PROXY_RETRY_INTERVAL` | `20` | 两次尝试之间的间隔（秒） |
| `PROXY_MAX_ATTEMPTS` | `200` | 防跑飞的保险丝，正常碰不到 |
| `PROXY_SILENCE_TIMEOUT` | `30` | 单次尝试等首字节的秒数 |
| `PROXY_HEARTBEAT_START` | `80` | 连续多少秒没有上游输入才开始发心跳 |
| `PROXY_HEARTBEAT_INTERVAL` | `80` | 上游无输入时每 N 秒补发一条，不限次数 |
| `PROXY_CONNECT_TIMEOUT` | `10` | 建连超时（秒） |
| `PROXY_SEND_TIMEOUT` | `90` | 发送请求体超时（秒） |
| `PROXY_RETRY_AFTER_CAP` | `60` | 采信上游 `Retry-After` 的上限（秒） |
| `PROXY_PORT` | `8787` | 监听端口 |

例：心跳提前到 60 秒、每 60 秒一次、重试窗口缩到 60 秒、每 10 秒试一次：

```bash
PROXY_HEARTBEAT_START=60 PROXY_HEARTBEAT_INTERVAL=60 PROXY_RETRY_WINDOW=60 PROXY_RETRY_INTERVAL=10 python src/retry_proxy.py
```

## 重启代理

**先确认没有请求在飞**：ZCode 自己的模型请求就走这个代理，正在生成的回答会被掐断。
判断方法（Windows）：`netstat -ano | findstr <代理PID>`，如果还有连到外部地址（非 127.0.0.1）的
`ESTABLISHED` 行，就说明有请求在处理，等它结束再动。`FIN_WAIT_2` 是收尾残留，不算忙。

**别手写 taskkill**。Windows 的 `SO_REUSEADDR` 允许两个进程同时监听 8787，
旧进程没死时新进程照样能绑上、`/__zp_health` 也会应答，"看起来换成功"其实跑的是旧代码。
用运维脚本，它只在没有在飞请求的空闲窗口动手，并确认旧进程消失**或 8787 端口已释放**才拉起新进程
（以端口为准：杀失败但端口已空时继续；端口仍被占就放弃）：

```bash
python "C:/Program Files (x86)/AI/Zcode-Persistence/restart_proxy_idle.py"
# 或者后台跑（当前对话自己的请求也走代理，前台跑会卡住自己）
```

脚本每次动作都写同目录的 `restart.log`：`idle:` 是等到窗口、`kill:` 是杀进程结果、
`restart: OK（… root=…）` 才算真的换成新代码（`root` 是脚本所在目录）。
`abort:` 表示旧进程没死透、或 8787 上不是本代理——此时它不会拉起新进程，需要人工处理。

**等不到空闲窗口时**（例如另一个会话的子代理一直占着上游连接）：加 `--force` 立即换进程。

```bash
# 放后台/另一个会话跑：--force 会掐断正在飞的请求，包括当前会话自己的
python "C:/Program Files (x86)/AI/Zcode-Persistence/restart_proxy_idle.py" --force
```

`--force` 只跳过"等空闲窗口"（在飞连接、`proxy.log` 静默、`MIN_ALIVE` 三项判据），
`kill:` 后仍要满足"旧进程消失或 8787 端口已释放"、只剩一个监听、`root` 指向安装目录，一条不少。
**代价**：在飞请求会被掐断，对应会话收到一次连接重置；客户端会不会自己续写取决于它，
尚无实测证据。`--force` 开始前会把目标 PID、在飞连接数、日志静默秒数写进 `restart.log`，
事后可核对影响面。2026-11-01 首次热更新就是这么做的，新 PID 起来后立刻接住了后续请求。

`安装目录` 为空时（端口没人监听）不用重启，下一次会话启动钩子会自己拉起。

## 看日志

| 文件 | 位置 | 内容 |
|---|---|---|
| 钩子日志 | `%TEMP%\Zcode-Persistence\hook.log` | `advise: n/3`、`cap: 已达上限`、`skip: 原因`、`error: 异常` |
| 钩子状态 | `%TEMP%\Zcode-Persistence\state.json` | 按"会话+命令"的计数，可直接删掉重置 |
| 代理日志 | `<安装目录>\proxy.log` | `ok path status=200 bytes=... first=x.xxs`、`attempt fail (...)` |

日志里出现 `attempt fail` 后面跟着 `ok` 是好现象——说明重发成功了。只有出现 `gave up after N attempts in Ns` 才是真失败（时间窗到点才收工）。

## 发版流程

1. 改代码
2. 更新 `VERSION`（语义化：修 bug 加 0.0.1，加功能加 0.1.0）
3. 更新 `CHANGELOG.md`，写清"改了什么 + 为什么"
4. 跑 `文档/04-测试记录.md` 的全部用例
5. 重新打包 ZIP，旧版本移到本机历史目录（仓库内不建 `历史/`；发行包走 Releases），不覆盖不删除
6. 在目标机器上 `install.py` 覆盖安装（脚本会被替换，配置里的钩子条目不会重复）

---

## 什么情况下该停手

出现以下任一情况，说明方案在恶化，应该回滚而不是继续打补丁：

- 代理反复崩溃，`proxy.log` 里出现成片的 `attempt fail` 且没有 `ok`
- provider 的 `baseUrl` 被 ZCode 界面改回去超过两次
- 会话中途出现"模型连不上"，而 `doctor.py` 显示端口未监听
- 你开始需要每天手动重启代理

回滚命令见 `01-安装与回滚.md` 的第三级。

## 报错汇报（error_watch）的启停与排障

这个组件**默认关闭**：装是装上了，但 `ensure_proxy.py` 只在环境变量
`ZCODE_PERSISTENCE_WATCH` 为 `1/true/yes/on` 时才拉起它。

```bash
# 打开开关（用户级，持久）：必须在**完全退出 ZCode 后**重新启动才生效，
# SessionStart 钩子继承的是 ZCode 进程的环境变量，当前会话不会因此改变
setx ZCODE_PERSISTENCE_WATCH 1

# 关掉：setx ZCODE_PERSISTENCE_WATCH 0 或删掉该用户变量
# （也可以只在当前 cmd 里临时设 set，然后手动前台跑下面这条）

# 手动前台跑（Ctrl+C 结束）——当前会话想立刻用就走这条，不依赖开关
cd /d "C:\Program Files (x86)\AI\Zcode-Persistence"
python error_watch.py

# 只诊断，不发信、不落状态
python error_watch.py --once

# 发一封链路自检邮件
python error_watch.py --test-mail

# 补报某个历史会话（不看基线/限流）
python error_watch.py --report-sid <会话 id> --proxy-log <proxy.log 路径>
```

查看状态与日志：

```bash
type "C:\Program Files (x86)\AI\Zcode-Persistence\error_watch.log"
# start: 启动 / baseline: 首轮忽略了多少历史红点 / cooldown: 冷却抑制
# ratelimit: 撞上限 / mail: 已发送或发送失败 / db: 会话库打不开或查询失败
```

停掉它：

```bash
# 按命令行找进程，别按端口（它不监听端口）
powershell -NoProfile -Command "Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*error_watch.py*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }"
```

常见现象：

| 现象 | 原因 | 处理 |
|---|---|---|
| 日志里一直 `cooldown` | 同一会话 10 分钟内只报一次，属正常 | 无需处理 |
| `ratelimit: 一小时内已发 8 封` | 故障期间刷屏保护 | 等下一小时，或调 `MAX_PER_HOUR` |
| `mail: 发送失败` | MCP 起不来 / 认证过期 / 网络 | 看后面的原因与 stderr 尾巴；`--test-mail` 复验 |
| 收到信但发件人是 QQ 地址 | `From` 没写成 outlook 地址 | 确认 `MAIL_FROM`，QQ 侧会丢弃伪造发件人 |
| 从没收到过邮件 | 只报了 `completed`/`interrupted`（这两类不报） | 用 `--once` 看当前有没有 error 会话 |

# 03 架构说明

## 整体位置

```
┌──────────────────────────────────────────────────────────────┐
│ ZCode Desktop                                                │
│                                                              │
│  模型请求 ──┐                                                 │
│             │  (模式 B 时 baseUrl = 127.0.0.1:8787/ap/v1)     │
│             ▼                                                 │
│      ┌──────────────┐        ┌─────────────────────┐         │
│      │ retry_proxy  │───────►│ upstream-a.example.com/v1   │         │
│      │ :8787        │  失败重发└─────────────────────┘         │
│      └──────────────┘                                        │
│                                                              │
│  工具调用失败 ──► PostToolUse(主)/PostToolUseFailure(兜底) ──► retry_hook.py │
│                                            │                 │
│                                            ▼                 │
│                                     additionalContext（建议重试） │
│                                                              │
│  会话启动 ──► SessionStart ──► ensure_proxy.py ──► 拉起代理   │
│                                                              │
│  会话报错（红点）──► error_watch.py ──► outlook MCP ──► 邮件  │
└──────────────────────────────────────────────────────────────┘
```

两条主链路彼此独立：钩子管**工具失败**，代理管**模型请求失败**。任一可以单独安装。
第三条是可选的旁路：`error_watch.py` 不参与重试，只在会话落到 `last_outcome=error`
（界面红点）时读代理日志、把原因发到邮箱；默认关闭（`ZCODE_PERSISTENCE_WATCH=1` 才启）。

## 模式 A：钩子链路

```
Bash 工具失败
   │
   ▼
ZCode 派发 PostToolUse（兜底事件 PostToolUseFailure），payload 含 tool_name /
tool_input / tool_response（exitCode、timedOut、status、stderr、stdout）
   │
   ▼
retry_hook.py 读 stdin JSON
   │
   ├─ 不是 Bash ─────────────────────────► 退出 0，静默
   ├─ 判定失败：退出码非 0 / timedOut / 取消 / status=failed|error
   ├─ 没失败 ─────────────────────────────► 退出 0，静默
   ├─ 同一 toolCallId 120 秒内已建议过 ────► 退出 0（去重）
   ├─ 计数已满 3 次 ──────────────────────► 退出 0
   ├─ UPSTREAM 命中 ──► 计数+1 ──► 输出"先等 3 分钟"建议
   └─ 其它任何失败 ──► 计数+1 ──► 输出"立刻重试"建议

计数规则：key = sha1(session | command)，上限 3，10 分钟窗口，1 天清理
v0.4.0 起没有 FATAL 过滤：任何失败都建议重试。
```

**为什么先剔 `tool_input`**：v0.4.0 起“要不要重试”只看退出码/超时/取消，与文本无关；文本只用于决定“要不要先等 3 分钟”（`UPSTREAM_PATTERNS`）。命令原文里若出现 `upstream_deadline` 之类的词，会让人误以为上游挂了，所以不参与匹配。

**为什么剔元数据字段**：`session_id`、`requestId`、`toolCallId` 是随机串，可能偶然拼出 `capacity`、`overloaded` 这类词，让“先等 3 分钟”的建议误发。剔除后判定只依赖真实输出。

**为什么永远退出 0**：钩子是旁路，它出问题不应该让会话停下来。所有异常在 `__main__` 外层被吞掉。

## 模式 B：代理链路

```
客户端 POST /ap/v1/chat/completions
   │
   ▼
读完整 body（兼容 Content-Length 与 chunked）
   │
   ├─ UA 是 python-* 或无 UA ──► 替换为常规浏览器 UA（绕 Cloudflare 1010）
   │
   ▼
┌─── 尝试 1 ──────────────────────────────┐
│ connect(10s) → send(90s) → 等首字节(30s) │
│  ✗ 连接失败 / 任何非 2xx 状态            │──► 重试
│  ✗ 30 秒没拿到响应头                     │──► 重试
│  ✓ 拿到响应头                            │──► 进入回写
└──────────────────────────────────────────┘
   │
   ▼
回写响应头（去掉 hop-by-hop）→ read1 逐块读、逐块 flush 给客户端
   │  （流式：reader 线程只做阻塞读，主线程每 0.5 秒看队列；
   │    静默满 80 秒补一条 `: keepalive`，满 180 秒判截断）
   │
   ├─ 流中途断 ──► 只能结束，不能重试（会造成内容重复）
   ├─ 定长响应少发字节 ──► 记 truncated，不补终止块
   └─ 正常结束 ──► 记 ok 日志
```

**v0.4.0 的重试判定**：任何失败的尝试都重发——连接异常、上游任何非 2xx、以及静默超时。不按次数，按时间窗：持续重试 3 分钟、每 20 秒一次（采信 `Retry-After`，上限 60 秒），窗口到点才收工；`MAX_ATTEMPTS=200` 只是防跑飞的保险丝。退避期间线程 `time.sleep` 等到下次尝试，不空转。心跳独立于尝试边界：连续 80 秒没有上游输入就发一条 `: keepalive`，之后每 80 秒一条，不设上限。

**关键设计：重试发生在"尚未向客户端写任何字节"之前。** 一旦开始回写就不能回头，这是 HTTP 流的物理限制，不是实现偷懒。

**30 秒静默超时的由来**：ZCode 客户端在 95 秒内拿不到首字节就判失败。因此代理在满 80 秒时先挂上 SSE 心跳注释行，把客户端的耐心续上。**响应头之前**的静默按 `SILENCE_TIMEOUT=30` 判失败并重试；**响应头之后**已经不能重试，静默改由“reader 线程 + 主线程消费队列”处理：每 80 秒补一条心跳继续等，累计静默满 `RETRY_WINDOW`（180 秒）才判截断。
前提是响应体确实是 SSE（`Content-Type: text/event-stream` 或已经由心跳模式发过 200 event-stream）；
否则插注释行会写坏正文，此时仍按 30 秒静默截断。

**时间窗不是硬上限**：`RETRY_WINDOW` 只决定"还发不发新尝试"。已经在飞的那次允许跑完（建连 10 秒 + 发送 90 秒 + 等头 30 秒上限），所以放弃时的实际耗时可能略超窗口；give-up 文案里的"已持续重试 N 秒"记的是真实耗时。

**最坏情况会超窗**：每次尝试还要花建连时间（上限 10 秒）和发送请求体时间（上限 90 秒）。如果上游是能连上但慢慢吞请求体，总耗时可能远超 95 秒，客户端会先超时。这种情况代理无法挽救，它只能保证快速失败的那些请求被重发。

## 自启动链路

```
ZCode 会话启动
   │
   ▼
SessionStart 钩子 → ensure_proxy.py
   │
   ├─ 8787 已被监听 ──► GET /__zp_health 验身份
   │                    ├─ 是本代理 ──► 退出 0（幂等）
   │                    └─ 不是本代理 ──► 写告警后退出 0（provider 会打到错误服务）
   ├─ 端口空闲 ──► subprocess.Popen(DETACHED_PROCESS) 拉起 retry_proxy.py
   └─ 任何异常 ──► 退出 0（不影响会话启动）
```

用 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` 是为了让代理脱离钩子进程存活——钩子跑完就退出了，代理必须继续在。

## 数据与隐私

| 数据 | 是否落盘 | 位置 |
|---|---|---|
| 模型请求/响应正文 | **不记录** | — |
| 工具错误文本 | 只记次数与类型（timeout/upstream/error），不落错误正文；异常分支只记异常类型 | `%TEMP%\Zcode-Persistence\hook.log` |
| 命令文本 | 只用于算 hash 做计数 key | `state.json`（仅 hash，不可逆） |
| 代理状态 | 只记状态码/字节数/延迟 | `<安装目录>\proxy.log` |

API Key 在 provider 配置里，代理只在转发时使用，不写日志。

## 与 ZCode 事件模型的关系

ZCode 支持七个钩子事件：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`PostToolUseFailure`、`Stop`。

本包用到三个：

- `PostToolUse`：**主挂载点**。本客户端对被中断/超时的 Bash 调用不派发 `PostToolUseFailure`，但 `PostToolUse` 一定来，且带结构化 `tool_response`（`exitCode` / `timedOut` / `status` / `stderr`）
- `PostToolUseFailure`：兜底，工具真正抛异常时才有
- `SessionStart`：唯一能稳定拿到"会话开始"时机的事件，用来拉起代理

**没有事件能捕获"整轮模型请求失败"**——`Stop` 只在正常结束时带 `responseText` 触发。这就是为什么模式 B 必须用代理在传输层解决，而不是用钩子。

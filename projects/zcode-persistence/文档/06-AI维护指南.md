## 2. 代码地图

### `src/retry_hook.py`（约 340 行）

ZCode 钩子，主挂 `PostToolUse`、兜底 `PostToolUseFailure`，`matcher="Bash"`。

```
main()
 ├─ 读 stdin JSON
 ├─ tool_name != "Bash" → 退出 0
 ├─ 判定失败（退出码非 0 / 超时 / 取消 / status=failed|error）
 ├─ 没失败 → 退出 0
 ├─ 同一 toolCallId 已建议过（120 秒内）→ 退出 0
 ├─ 计数已满 3 次 → 退出 0
 ├─ UPSTREAM_RE 命中 → 建议"先等 3 分钟再重试"
 └─ 其它任何失败 → 建议"立刻原样重试"
```

v0.4.0 起只剩一个模式列表 `UPSTREAM_PATTERNS`（命中则建议先等 3 分钟再发）；**要不要重试不由模式决定**——任何失败都建议重试，上限 3 次。计数状态在 `%TEMP%\Zcode-Persistence\state.json`，key 是 `sha1(session|command)`。

### `src/retry_proxy.py`（约 710 行）

本地 HTTP 代理。请求进来 → 按前缀选上游 → 转发 → 失败重发。

```
Handler._safe_handle()          ← 客户端断开在这里收成一行日志
 └─ Handler._handle()
     ├─ 解析 /ap 或 /cm 前缀 → (host, port, scheme)
     ├─ 读完整 body（兼容 chunked）
     ├─ UA 兜底（python-urllib → 浏览器 UA）
     ├─ 解析 body.stream 判断是否流式
     └─ 主循环（while True）
         ├─ 窗口到点且没有在飞的尝试 → 收尾
         ├─ 到点就发起一次尝试（子线程跑 fetch_once，主线程轮询）
         ├─ 拿到结果：ok → pipe_response；失败 → 记录 reason
         ├─ 窗口到期或 attempt >= MAX_ATTEMPTS（保险丝 200）→ 收尾
         ├─ 心跳检查（独立时钟 next_hb_at）
         └─ 每次重试前等 RETRY_INTERVAL（20 秒；Retry-After 更大则听它的）后下一轮

pipe_response()                 ← 响应头已发，不能再重试
 ├─ read1(8192) 逐块回写（不能攒批）
 ├─ 流式：起 reader 线程只做阻塞读 → queue_；主线程每 0.5 秒看一次队列
 │   ├─ 静默满 HEARTBEAT_INTERVAL → 写 `: keepalive`
 │   └─ 静默满 RETRY_WINDOW      → 收尾判 truncated（不等 reader；它在 put 处看 stop 退出）
 └─ 收尾：完整 → 补 `0\r\n\r\n`；短读/异常 → 不补，记 truncated
```

`fetch_once()` 返回 `Attempt(reason=...)`，reason 有五种：`ok` / `connect` / `silence` / `status` / `other`。**reason 决定后续行为**：只有 `silence` 会触发"等太久"的语义。

### `src/error_watch.py`（约 620 行）

报错汇报：轮询 `~/.zcode/cli/db/db.sqlite` 的 `session.last_outcome`，值为 `error`
（界面红点）时把原因邮件发到 `your-email@example.com`。默认不自启，`ZCODE_PERSISTENCE_WATCH=1` 才由 SessionStart 拉起。

- 状态机（最容易改错的地方）：`seen` 只在**发送成功**后推进到该会话的 `time_updated`；
  冷却 / 限流 / 发信失败 / `--no-send` 都**不推进**，报错留在 pending 等下一轮。
- `sent_at`：会话级冷却（`SESSION_GAP=600`），防同一次故障连发几十封。
- `sent`：最近一小时的发送时刻，用来做 `MAX_PER_HOUR=8` 的限流。
- `retry_after`：发信失败后的退避（`MAIL_RETRY_GAP=60`）。
- `logged`：日志节流标记，冷却/限流/发送失败类提示默认 600 秒一条（按会话或会话集合），避免 5 秒轮询刷屏。
- `baseline`：首次启动只把 `FRESH=180` 秒内的红点当"刚发生"，更早的只记基线；查询失败不置基线。
- 原因解析依赖 `proxy.log` 的**带日期**时间戳（`LOG_TS_RE`），只接受报错时刻前后
  `CAUSE_WINDOW=900` 秒内的 `gave up` / `attempt fail`；老格式（只有时分秒）仍兼容，但超过一天的旧日志可能算错。

### `src/ensure_proxy.py`（约 110 行）

`SessionStart` 钩子。端口被监听 → 退出 0；否则以 `DETACHED_PROCESS` 拉起代理。任何异常都吞掉，保证不拖慢会话启动。

### `tools/`

- `install.py`：先校验（配置存在、源文件存在、provider 存在、前缀可判定）→ 再落盘（复制脚本、写钩子、改 provider）→ 最后写 `install-state.json`。配置解析失败会在写盘前退出。
- `uninstall.py`：按 basename 精确删钩子；provider 只在"当前值 == 记录的 proxyBaseUrl"时还原；`--purge` 会先核对进程命令行再杀，且只认"目录里确实有本工具文件"的 prefix 记录。
- `doctor.py`：脚本、解释器、`hooks.enabled`、三处钩子（两个工具钩子校验 matcher=Bash，三处都校验脚本路径）、provider、端口、代理运行参数、日志尾巴。日志尾巴只读末尾 64KB；找“启动行”会从文件末尾按 64KB 分块回看，上限 8MB。
- `selftest_proxy_429.py`：重试语义五场景（429 恢复 / 持续 429 / 400 恢复 / 持续 400 / 未知前缀 400 必须 `retryable:false`）。
- `selftest_stream.py`：流式回写七场景（逐条透传 / 流中静默续命 / 定长短读判截断 / 正常收尾 / 静默到窗口判截断 / 慢客户端不丢数据 / 心跳模式下放弃必须带可重试错误体）。
- `selftest_watch.py`：报错汇报 12 条断言（新红点 / 去重 / 历史基线 / 完成与停止不报 / 限流 / 多会话合并 / 无相关记录措辞 / 有失败未放弃·新格式 / 同上·旧格式 / 冷却与过期 / 发信失败重试 / `--once` 不落盘）。

## 3. 不变量（改之前先读）

这些是被踩过坑之后固化下来的，破坏其中任何一条都会导致已知故障：

| # | 不变量 | 破坏后的症状 |
|---|---|---|
| 0 | 钩子挂 `PostToolUse` + `PostToolUseFailure`，按 `toolCallId` 去重 | 只挂 Failure → 永远不触发（本客户端不派发超时/中断） |
| 1 | 心跳是 SSE 注释行 `: keepalive` | 改成 `data:` 会被当成模型说的话，污染回答并长期留在上下文 |
| 2 | 心跳由独立时钟驱动，且**连续 80 秒无上游输入才发、不限次数** | 挂在尝试边界上会晚一个周期；改成固定次数则在长等待里会断流 |
| 3 | 钩子所有路径退出码 0 | 一旦返回 2 或异常，会话被阻断 |
| 4 | 钩子匹配用 basename 精确相等 | 用子串会把 `my_retry_hook.py` 误判为已安装/被删除 |
| 5 | install 先校验后落盘 | 中途 `die()` 会留下"钩子已装、state 未写"的半成品 |
| 6 | uninstall 精确还原条件 | 放宽后会把用户手动改过的地址覆盖掉 |
| 7 | 不记录请求/响应正文 | 泄漏对话内容与密钥 |
| 8 | TLS 用 certifi | Windows 根库缺 SSL.com，代理直接连不上 |
| 9 | UA 兜底 | 中转 Cloudflare 拦 `Python-urllib`，回 1010 |
| 10 | 钩子输出只能用 `additionalContext` | 用 `systemMessage` 模型看不到，等于没建议（v0.3.0 的坑） |
| 11 | **不要按错误类型筛除**：任何失败都建议重试 | 加回 FATAL 过滤就违背“任何报错都重试三次”的需求 |
| 12 | 代理对**任何非 2xx** 都重试 | 改回白名单会让 4xx 直接弹窗，用户看到未重试 |
| 13 | 退避期必须 `sleep` 等待 | 空转会打满单核（v0.3.1 实测 97%） |
| 14 | 回写响应体用 `resp.read1(n)`，不用 `resp.read(n)` | `read(n)` 会攒满 8KB 才返回，SSE 看起来不流式 |
| 15 | 响应体读取放在独立线程（`reader()` → `queue_`），主线程消费 | 主线程阻塞读就没法按时心跳、也没法到点收尾 |
| 16 | 不能用 socket 超时判静默 | 超时后缓冲流不可续读；chunked 的 `readline` 还会丢半行导致 `IncompleteRead` |
| 17 | 不要从别的线程 close/shutdown 打断读 | Windows 上叫不醒，还会和 `BufferedReader` 的锁互等 |
| 18 | 短读要判 `resp.length` | 定长响应提前 EOF 不抛异常，会被当成完整响应并补终止块 |
| 19 | 取上游 socket 走 `body_socket()` | 上游回 `Connection: close` 时 `conn.sock` 为 `None`；它只用于设置泄漏保险超时 |

## 4. 测试配方（改完必跑）

不需要真实中转。**关键技巧**：把心跳起点设得比单次静默更小（`START=2` < `SILENCE=3`），如果心跳仍在 2 秒左右出现，就证明它是独立时钟驱动、没有等某次尝试失败。

```python
import importlib.util, json, os, socket, sys, threading, time

SRC = r"<包目录>/src/retry_proxy.py"      # 用正斜杠，避免路径转义问题
os.environ.update(
    PROXY_SILENCE_TIMEOUT="3",           # 单次静默 3 秒
    PROXY_HEARTBEAT_START="2",           # 心跳起点 2 秒（故意小于静默，用于证明时钟驱动）
    PROXY_HEARTBEAT_INTERVAL="2",
    PROXY_RETRY_WINDOW="3",              # 重试时间窗 3 秒，测试用极短值
    PROXY_RETRY_INTERVAL="0.2",          # 两次尝试间隔 0.2 秒
    PROXY_PORT="18795", PROXY_CONNECT_TIMEOUT="2")
sys.dont_write_bytecode = True           # 不在包里留 __pycache__
spec = importlib.util.spec_from_file_location("rp", SRC)
m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)

srv = socket.socket(); srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 18796)); srv.listen(20)
threading.Thread(target=lambda: [srv.accept() for _ in iter(int, 1)], daemon=True).start()
m.UPSTREAMS.clear(); m.UPSTREAMS["/t"] = ("127.0.0.1", 18796, "http")
threading.Thread(target=m.main, daemon=True).start(); time.sleep(0.8)

body = json.dumps({"model": "m", "stream": True,
                   "messages": [{"role": "user", "content": "hi"}]}).encode()
NL = b"\r\n"
req = (b"POST /t/v1/chat/completions HTTP/1.1" + NL + b"Host: x" + NL +
       b"Content-Type: application/json" + NL +
       b"Content-Length: " + str(len(body)).encode() + NL + NL) + body
s = socket.create_connection(("127.0.0.1", 18795), timeout=20); s.sendall(req)
s.settimeout(0.3)

t0 = time.time(); raw = b""; hb = []
while time.time() - t0 < 20:             # 单次静默 3 秒 → 第一次失败即到窗口，约 3.2 秒收尾；20 秒余量充足
    try:
        d = s.recv(4096)
        if not d:
            break
        raw += d
        while b"keepalive" in raw:
            hb.append(round(time.time() - t0, 2))
            raw = raw.replace(b"keepalive", b"", 1)
    except socket.timeout:
        pass
s.close()

print("心跳时刻:", hb)
print("断言1 不早于起点2秒 :", bool(hb) and all(t >= 1.7 for t in hb))
print("断言2 早于静默3秒   :", bool(hb) and hb[0] < 3)
print("断言3 窗口收尾      :", "已持续重试".encode() in raw)
print("断言4 有错误事件    :", b"server_error" in raw)
```

**参数选择理由**：`HEARTBEAT_START=2` 故意小于 `SILENCE_TIMEOUT=3`。如果心跳仍能在 2 秒左右出现（而此时第一次尝试要到 3 秒才失败），就证明心跳不依赖尝试边界。时间窗 3 秒配单次静默 3 秒，第一次尝试一失败（t≈3.0 秒）下一次尝试的时点（t≈3.2 秒）就已越过窗口，于是立刻收尾——正好把"窗口到期"这条路径单独测出来，观察窗口取 20 秒余量充足。

**四条断言**

| 断言 | 证明什么 | 不成立说明什么 |
|---|---|---|
| 1. 所有心跳 ≥ 起点（留 0.3 秒容差） | 心跳不提前 | 时钟阈值比较写错 |
| 2. 首次心跳早于静默超时 | 心跳不等尝试失败 | 心跳被挂回尝试边界（历史 bug） |
| 3. 响应里出现 `已持续重试` | 时间窗收尾生效 | RETRY_WINDOW 逻辑被改坏 |
| 4. 响应里出现 `server_error` | 全失败给明确错误，不挂死 | 收尾路径丢了 |

非流式对照：把 `stream` 改成 `False`，期望 **无** `keepalive`，窗口到点后返回 HTTP **503**（普通 JSON，不是 SSE；加速参数下约 3 秒）。

**响应体（流式回写）另有一套自检**：`python tools/selftest_stream.py`，七个场景分别压"逐条透传 / 流中静默续命 / 定长短读判截断 / 正常收尾 / 静默到窗口判截断 / 慢客户端不丢数据 / 心跳模式下放弃必须带可重试错误体"。改动 `pipe_response` 之后必须跑它——响应头之后的行为在这套配方里测不到。

## 5. 故障定位

| 症状 | 先查 | 常见原因 |
|---|---|---|
| 模型完全连不上 | 8787 是否监听；`doctor.py` | 代理没起 / provider 已指向代理但端口空 |
| 还是弹"95 秒没有产出" | `proxy.log` 有无 `heartbeat #` | 心跳没触发（非流式请求不发心跳），或单次尝试的建连+等待已超过 95 秒 |
| 钩子不触发 | `doctor.py` 的钩子项；`hook.log` | `hooks.enabled=false` / 挂在错误事件 / 非 Bash 工具 |
| 日志里有 `attempt fail` 但最后 `ok` | 正常 | 说明重试救回来了 |
| 日志里有 `truncated` | 正常 | 已开始回写后断流，不能重试 |
| `install.py` 报"未做任何改动" | 看报错原文 | 校验阶段退出，属预期行为，按提示补参数 |
| provider 地址被改回官方 | 重跑 `install.py --with-proxy` | ZCode 界面可能重写该文件 |

日志位置：`%TEMP%\Zcode-Persistence\hook.log`（钩子）、`C:\Program Files (x86)\AI\Zcode-Persistence\proxy.log`（代理）。

## 6. 修改与发版流程

1. 改代码。
2. 跑第 4 节测试，四条断言全过。
3. 手动喂样本验钩子（改过模式列表时必做）：
   ```bash
   echo '{"tool_name":"Bash","tool_input":{"command":"curl x"},"error":"operation timed out"}' | python src/retry_hook.py
   ```
4. 升版本：`VERSION` 与 `tools/install.py` 的 `VERSION` 两处。
5. 更新 `CHANGELOG.md`（写清改了什么、为什么）。
6. 同步 `README.md` / `文档/02-维护手册` 里受影响的参数表。
7. 打包：用下面的脚本（脚本名 `make_zip.py` 放到包目录同级执行即可，记得改版本号）。

```python
import os, zipfile
root = os.path.dirname(os.path.abspath(__file__))
with zipfile.ZipFile("Zcode-Persistence-vX.Y.zip", "w", zipfile.ZIP_DEFLATED) as z:
    for dp, dns, fns in os.walk(root):
        dns[:] = [d for d in dns if d != "__pycache__"]
        for fn in fns:
            if fn.endswith((".pyc", ".log")):
                continue
            z.write(os.path.join(dp, fn), os.path.join("Zcode-Persistence-vX.Y",
                    os.path.relpath(os.path.join(dp, fn), root)))
```

8. 交独立子代理复核（综合与代码两项均 ≥4.5/5 才放行），低于标准就改完重来。

## 继续开发从这里开始（给下一个 AI / 工程师）

**先搞清版本号**：对外发正式版号（V0.2），代码里的 `0.4.0` 是构建线迭代号，
两者不是一套东西。`VERSION` 文件与 `tools/install.py` 的 `VERSION` 都写正式版号；
`CHANGELOG.md` 顶部的映射条目会告诉你当前正式版对应哪条构建线。

**五分钟上手**

1. 读 `README.md` 的「它是什么 / 限制」两节。
2. 读本文件（`文档/06-AI维护指南.md`）第 2 节代码地图和第 3 节不变量。
3. 跑一次体检：`python <安装目录>/doctor.py`，应 11 项通过、0 失败。
4. 跑自检：`tools/selftest_proxy_429.py`（5 场景）、`tools/selftest_stream.py`（7 场景）、
   `tools/selftest_watch.py`（12 断言）应全 PASS。

**改代码前必须知道的三件事**

- 钩子只“建议”重试，真正重发的是代理；两者互不依赖，可以单独装。
- 钩子输出**只能用 `additionalContext`**；写成 `systemMessage` 模型看不见（v0.3.0 踩过）。
- **不许按错误类型筛除**。任何失败都建议重试；代理对任何非 2xx 都重发。

**改完的标准动作**

1. `python -m py_compile src/*.py tools/*.py`
2. `python -I tools/selftest_proxy_429.py`（重试语义）
3. `python -I tools/selftest_stream.py`（流式回写）
4. 跑 `文档/06-AI维护指南` 第 4 节的心跳配方（四条断言）
5. `python tools/install.py --with-proxy --provider-id new-provider`
6. 重启代理（改的是 `retry_proxy.py` 才需要）：按 `文档/02-维护手册` 的「重启代理」，**不要在请求在飞时杀进程**

## 8. 已知边界（不是 bug，别去"修"）

1. **钩子接不住整轮失败**。`PostToolUseFailure` 需要 `toolName`/`toolCallId`，模型层的 `Turn execution failed` 没有工具参与，七个钩子事件都不触发。这类只能靠代理。
2. **代理救不了"上游慢慢吞请求体"**。95 秒是客户端硬超时，代理无法让上游变快。
3. **心跳只对流式有效**。非流式响应必须是完整 JSON，中途插不了东西。
4. **心跳在 80 秒时上线**，客户端 95 秒超时之后就不再计时；响应头之后如果上游长时间不吐字节，由 reader 线程+主循环继续发心跳，静默累计到重试窗口（180 秒）才判截断。
5. **provider 配置可能被 ZCode 界面重写**，重跑 `install.py --with-proxy` 即可恢复。
6. **`retryable` 由本地决定，不是上游**（2026-10-31 更正）。代理放弃时自己回
   `code=model_server_error` + `retryable:true`，客户端才会用流恢复重试并续写；
   旧版本把客户端弹窗里的 `retryable=false` 当成"上游决定"，导致整轮被判死。
   400（客户端自己写错）仍回 `retryable:false`。
7. **Windows 的 `SO_REUSEADDR` 允许两个进程同时绑定 8787**（Linux 上不允许）。所以"端口监听中"不等于"跑的是本代理"：`ensure_proxy`/`doctor` 都会先请求 `/__zp_health` 确认。出现两份代理时按 `netstat -ano` 的 PID 杀掉多余的，别两个都留。
8. **时间窗不是硬上限**。`RETRY_WINDOW` 只决定"还发不发新尝试"；已经在飞的那次允许跑完（建连 10 秒 + 发送 90 秒 + 等头 30 秒上限），所以最坏耗时可能超出窗口。
9. **`proxy.log` 不轮转**。长期运行会一直增长；`doctor` 只读尾部（启动行最多回看 8MB），需要清理时直接删掉即可（代理会重新创建）。
10. **响应体心跳只对 SSE 生效**。`can_hb` 要求客户端要流式且响应是 `text/event-stream`（或心跳模式已发过 200）；
    其它 Content-Type 插注释行会把正文写坏，那种情况仍按 `SILENCE_TIMEOUT=30` 秒截断。
11. **读取线程与队列**。`pipe_response` 用 `Queue(maxsize=64)`（约 512KB）连接读取线程和主线程；
    队列满时读取线程阻塞（背压），不会丢数据。主线程收尾后置位 `stop`，读取线程在下一次 `put` 时退出；
    若它正卡在阻塞读，只能等 socket 超时（`RETRY_WINDOW+30` 秒）——这是 Windows 上无法从外部打断 `read1` 的必然代价。
    另：客户端“不读也不断开”（半开）时主线程会阻塞在 `wfile.write`，直到对方恢复或 TCP 报错；没有客户端写超时是既有边界。
    降级：`body_socket()` 取不到 socket 时读超时仍是 `SILENCE_TIMEOUT=30`，响应体心跳基本失效。

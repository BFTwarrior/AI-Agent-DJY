# Known limits

These are physical, environmental, or deliberate product limits. They are not bugs to "fix" by hand-waving.

## Physical

- A tool call already executing cannot be edited. It can only finish, be cancelled, or be killed.
- Containers share the host kernel. They protect against model mistakes and cross-member interference, not kernel exploits. Use a microVM (Kata/gVisor/Firecracker) for a stronger boundary.
- A model's context grows. Member sessions must be compacted or replaced with a summary; long-lived sessions are not free.

## Native Subagents acceptance boundaries (introduced in 0.1.11)

- Native `team-worker` is one shared model preference, not a native session row per roster member. Its Settings visibility requires a manual full-plugin update; source tests and runtime hot updates cannot establish host resource registration.
- Explicit native selections require Protocol model switching. CLI/container workers refuse such a pin; their existing non-native configured execution remains unchanged. A provider may still reject a structurally valid selection, and paid-model acceptance has not been exercised by this refactor.
- The Protocol adapter forwards structured provider/model IDs verbatim after non-empty validation; direct callers own normalization. The native Settings reader separately normalizes its host-state input before signing it. Neither path may split structured IDs back from a display string.
- A Settings change cannot retract a provider request already accepted by `adapter.send`. The daemon reconciles selection before subsequent worker dispatch, continue and mail sends; it does not claim to undo an in-flight turn.
- `src/install-wizard.mjs` content comparison includes the restored `agents` resource root, but its existing digest scope does not include `hooks/`, `prompts/` or `scripts/`. `contentOk` alone is not full-package integrity proof. Extending that installation contract is separate from this module/native-model change.
- Existing hot-update lock expiry precedence and pointer-temp crash cleanup remain separately identified maintenance work; this refactor does not claim to solve every crash or hostile-host scenario.
- Windows staging publication has bounded `EPERM`/`EBUSY` retries; the original full-run denial's OS cause was not established. The 1000 ms budget bounds starting retries, not an already executing filesystem call. Target/identity checks preserve observed competing targets but are not an atomic no-replace primitive against writers bypassing the runtime lock. New journals without a usable matching identity retain the ambiguous recovery state instead of deleting it.

## Capacity

- 32 roster rows is not 32 concurrent workers. The default is six active workers.
- 16 active workers requires more CPU/RAM and provider concurrency; it is a load-test target, not the default.
- 32 active workers is a multi-host target. Two single-machine 32/32 runs (paced and unthrottled) passed on 2026-10-29, but that is not a guarantee across hosts, providers, or quotas; multi-host load is not tested.
- Six containers at 2 CPU / 2 GB each is already substantial; size the host accordingly.

## Environment

- The original verification host had no Docker/WSL; as of 2026-10-30 WSL 2.7.14 + Podman 5.8.3 are installed and hard container execution is verified for writable work tasks. A remote Linux host remains untested.
- Container dispatch is wired through `src/session/container-cli.mjs` and `src/runtime/container.mjs`. Real execution requires WSL2 + Podman/Docker, a worker image containing a compatible Linux ZCode CLI, `isolation.homeSeed` + `isolation.workerModel`, and a passing self-test. `deploy/worker.Dockerfile` builds the Linux CLI from a pinned upstream ZCode source revision; this is not an official prebuilt worker image or an automatic CLI version feed. `isolation.imagePullPolicy` optionally pulls a configured trusted image reference at startup; updating the CLI requires rebuilding that image. Read-only analyst/reviewer roles use `plan` mode and cannot call team-cli, but they receive the member MCP server through the worker home; a read-only `verification` task completed this way on 2026-10-30.
- ZCode CLI/protocol is a moving target. A version change can remove a method; the capability probe must fail closed or degrade with a warning.
- ZCode 0.17.0 does not expose a maximum-subagent setting in config, `runtime/capabilities`, or `zcode doctor`. The installer can only recommend from hardware/provider limits; it must not invent a platform maximum.
- ZCode 0.17 has no conversation-header contribution slot. It does support native plugin UI surfaces (`ui.surfaces` with `availability: "session"`), which appear in the session side pane's `新增标签` menu and open as a side-pane tab. The plugin declares this surface; the exact header row remains host-owned.
- ZCode 0.17's `ui.surfaces` schema has **no** `autoOpen`/`openOnStartup` field. Startup uses a plugin `SessionStart` hook (`hooks/hooks.json` + `scripts/session-start.mjs`) that injects a one-time call instruction into a new session; the `agent_teams_view` tool declaration carries `_meta.ui` `surface` + `preferredDisplayMode: "fullscreen"`, which the host maps to the side-pane opener. This is model-mediated: if the model skips the first call, `/team-view` is the manual fallback, and this is not a host-guaranteed popup. The hook is suppressed in worker sessions (`AI_AGENT_TEAMS_WORKER=1`), fires in a workspace with `.ai-agent-teams/` or a `config/local.json` containing this tool's `teams` array, **or when a live team daemon exists** (the default-workspace fallback), and can be disabled with `AI_AGENT_TEAMS_AUTO_PANEL=0` (`=1` forces it elsewhere). MCP `initialize.instructions` carries the same rule as a secondary hint, but ZCode 0.17.1's consumption of that field is unverified.
- ZCode 0.17's MCP App host accepts `inline|fullscreen|pip` in the schema but does not implement pip; `agent_teams_view` requests fullscreen and deliberately omits `showInline`, because that flag pins an inline card. Hosts that do not open the side pane still get the Markdown view link, not a guaranteed inline card. A true always-on-top floating window still requires a host-side surface.
- An empty git repository gets an empty baseline ref (`createWorktree`/`ensureWorktreeBase`, object-format aware, create-only so concurrent dispatchers cannot overwrite it) so the first worktree dispatch can start. The baseline deliberately does **not** commit untracked project files (that would copy secrets and large artifacts); a non-empty repository with a missing `baseBranch` is blocked by `worktreeBaseCheck` before an attempt, records `worktree.base_missing`, and leaves the task pending with `blocked: worktree-base-missing` instead of creating a guessed branch. Checks are cached (default 30s, exponential backoff on failure) and skipped when no task is pending.

## Product

- v0.6 is implemented behind feature flags in `config/example.v06.json`; legacy configs still pre-create roster rows and use 6 slots / 3 per team.
- A packaged read-only `/ui` team view exists via `/team-view` (live snapshot + SSE), and the plugin declares a native side-pane surface for the same panel. `/ui` now requires a per-process access key before it serves the snapshot; the first visit uses a loopback URL and then an HttpOnly cookie, so another local OS account cannot open the panel just by reaching loopback. A six-worker real-model smoke passed; a rate-limited 16-way run passed 16/16, and the 2026-10-29 real 32-way run passed 32/32 with pacing and 32/32 unthrottled on `provider-a/model-x`. Other providers/runs can still hit group RPM limits. Real app-server `session/compact` wait and close→`session/resume`→send are verified with `npm run zcode:lifecycle`; hard container execution is verified for writable work tasks and read-only MCP completion, while multi-host load remains unverified.
- Member-scoped tokens prevent direct admin API calls, but daemon and members share the same OS user; a member that reads the 0600 discovery file can recover the admin token. The panel key is not a substitute for a separate OS user or a per-member credential boundary.
- `toolPolicy` and license `pathScope` are metadata/prompt constraints; member protocol sessions do not yet enforce them at the tool layer. The MCP server list is restricted to a member-scoped `agent-teams-member` server, and the plugin admin server is denied by exact tool name, but this is tool-surface reduction, not OS isolation.
- Same-process `turn.failed` retry is implemented for the app-server/Protocol adapter; the watcher forwards `message`, `code`, `type`, `retryable`, and a normalized `retryAfterMs`. Capacity classification prefers structured codes and types such as `rate_limit_exceeded`; keyword matching is only a fallback, is suppressed by clear non-capacity codes (for example `E_INVALID`) and filesystem messages such as `EMFILE`/`ENOSPC`, and a positive retry hint is treated as capacity. `retryable: false` fails immediately. A provider retry hint overrides the local backoff, capped at one hour even if `maxDelayMs` is lower. Normal failures use `zcode.turnFailureRetry.maxAttempts` (default 3); capacity/429 failures use `capacityMaxAttempts` (default 3), reduce `activeWorkerSlots` before retrying, and wait for a real free slot. The reduced value is persisted in `.ai-agent-teams/runtime-capacity.json`; after `capacityRecoveryMs` (default 60s) and `capacityRecoverySuccesses` (default 3) consecutive successful turns, one slot is restored, repeating up to the configured ceiling. Invalid, corrupt, or configuration-mismatched state files are ignored. Dispatch-time `adapter.create`/`send` errors use the same retry path. The CLI adapter has no live event stream, but its `send` call is synchronous: JSON provider errors and JSON error payloads from nonzero exits are returned/preserved and retried without waiting for the lease; plain-text stderr yields the message and known codes but no retry hint. Mid-turn events and `guide` are unavailable; it fails closed if a member session has no member token.
- ZCode 0.17 may expose the plugin `agent-teams` MCP server even when an explicit empty `mcpServers` array is sent. Member sessions therefore deny `mcp__plugin_ai-agent-teams_agent-teams__*`; contractors deny `agent_teams_*`, `mcp__agent-teams__*`, `mcp__agent-teams-member__*`, and `mcp__plugin_ai-agent-teams_agent-teams__*` instead of claiming MCP is disabled. This is a tool-boundary mitigation, not a process/OS boundary.
- `delivery: "queue"` is a scheduler-level defer/retry convention. The app-server `session/send` call has no explicit queue parameter; a send while a member turn is active can be rejected, and the next tick retries it if the message/task is still pending.
- Hard container isolation is verified for workspace-write `work` tasks on this host (WSL2 + Podman, seeded worker home/model, bridge/NAT callback). It still needs `isolation.homeSeed` and `isolation.workerModel`; read-only analyst roles use `plan` mode and cannot call team-cli; they complete tasks through the member MCP server instead. A selected provider that only listens on host loopback can be reached through a narrow TCP bridge; the worker provider URL is rewritten to the bridge, but `gateway-only` is still bridge/NAT with unfiltered outbound egress, and each worker home contains a host ZCode credentials copy; remove/archive purges it. Treat the host as trusted and do not claim a firewalled security boundary.
- The loopback provider bridge is only started in `gateway-only` mode and only binds an explicit `hostAddress` or a strict WSL/Hyper-V address (never an arbitrary LAN adapter). It is a TCP forwarder without an application-level authentication layer: any process or container that can reach that interface can use the forwarded provider proxy. Do not set `hostAddress` to a LAN address; `network=none` and a genuinely remote `containerUrl` skip the rewrite. Loopback and `host.docker.internal`/`host.containers.internal` container URLs are treated as local. Container-host detection currently looks at IPv4 interfaces, so an IPv6-only container network fails closed with a warning.
- The MCP `agent_teams_view` button needs the keyed `viewUrl`; that key therefore appears in the tool's structured result and Markdown link (not the admin token or page HTML). `initialize.instructions` is redacted and points to `panel --open`.
- The saved workspace target (`~/.ai-agent-teams/active-workspace.json`) is per OS user, not per ZCode conversation. It is only a fallback: a session with its own team config ignores it, but two bare/global sessions share the last `use` choice. `agent_teams_workspace` is hidden from member sessions; a member that can read the 0600 discovery file still has the same OS-user access described above.
- State can still accumulate: managed member homes for current roster rows are kept; a home is reclaimed on member removal/archive, or by the opt-in `scheduler.memberHomeReclaimMinutes` sweep only when ownership is proven and the member row is absent. Unmarked legacy homes are not automatically swept. Startup also removes only empty, inactive workspace-discovery directories older than seven days. `supervisor.log` rotates at 5 MiB with one backup, while `pruneEvents(50000)` caps non-archived event rows at daemon startup; archived-team history is exempt, so the physical table may exceed 50,000 rows. Pruning does not necessarily shrink the SQLite file. Broader cleanup is a user-confirmed manual step with a fixed keep-list, documented in `docs/known-limits.md` and summarized for agents in `skills/agent-teams/SKILL.md`.
- An explicit `AGENT_TEAMS_URL`/`AGENT_TEAMS_TOKEN` (member servers) bypasses workspace discovery, so `agent_teams_workspace` cannot redirect those connections.
- The standalone panel window needs Edge/Chrome (`--app`). Without a Chromium browser the opener falls back to the OS default and reports `mode: "tab"`, not an app window.
- MCP auto-restart on a connection failure retries a non-idempotent POST only when no daemon was healthy and a new process actually started. Only `not configured`, `ECONNREFUSED`, `ENOTFOUND`, or `EAI_AGAIN` (including nested undici causes) may trigger `ensureDaemon`; a real `UND_ERR_HEADERS_TIMEOUT`/`UND_ERR_BODY_TIMEOUT`/`AbortError`, a generic `fetch failed`, or any request that reached a healthy daemon is reported, not probed, killed, or replayed, because the daemon may already have accepted it.
- Task `verify` commands run on the daemon host. Do not run untrusted task contracts without a container/allowlist.
- Integration-branch review fast-forwards the currently checked-out base branch; if the repository is on another branch, the merge stops in `ff_failed` instead of forcing a checkout.
- A `read-only`/`review` contractor's write barrier is the tool denylist (`Edit`/`Write`/`MultiEdit`/`ApplyPatch`/`apply_patch`/`NotebookEdit`), not an OS sandbox: `Bash` stays available so a reviewer can run tests and git inspection, which means a shell command can still write inside the worktree (`echo > file`, a build script). The worktree/container boundary is the isolation boundary; deny shell access only by accepting that no review can run its own checks, and use a container for untrusted work.
- The CLI adapter's tree kill is best-effort by platform: Windows uses `taskkill /PID <pid> /T /F`, POSIX signals a detached process group. A process that double-forks or escapes the group can survive; the container path should be used where that matters.
- v1 forbids cross-team task dependencies. Only messages cross teams.
- A staged plan cannot self-approve; a human must approve it.
- Merging conflicts are not auto-resolved; an integrator/repair task is created.
- The last formal release was 0.1.8; current source/package metadata is 0.2.2 and unreleased. Neither is production-ready. Historical evidence includes a fake-adapter backend suite, a six-worker app-server smoke, a paced 16-way run, and 2026-10-29 real 32-way runs (32/32 paced and unthrottled). Hard container execution was verified for writable work tasks and read-only MCP completion; multi-host load remains unverified, and other provider quotas can still limit throughput. See the dated records in `docs/status/STATUS.md` and `docs/verification.md`.
- The package is not production-ready and has no real-user benchmark.
- `contractors.reviewPool` is a reserved configuration shape, not a wired capacity source: the slot helpers currently receive `contractors.slots` only, and the config validator rejects an enabled review pool. Do not enable it expecting extra review capacity without first wiring the pool through `contractorSlotFor`/`contractorSlotCap`/`contractorPools`.
- Worktree publication is a compare-and-swapped branch ref plus a separate `reset --hard` of the checkout. If the ref advances but the checkout sync fails (`worktreeSynced:false`), the task is escalated with the exact `git reset --hard <commit>` command; later publications will see a dirty target until an operator runs it. The fence itself is a lock file plus worktree fingerprint, not a kernel-level freeze. The tracked-dirty check runs before the ref CAS; a writer that appears between the check and the reset can still be overwritten (the reset cannot be preceded by a meaningful post-CAS status check because the checkout is then behind the new ref).
- A fence acquired with `requireProvenance:false` (worktree-style completion without delivery trailers) accepts any commit descendant of the base, including one an external writer made after acquisition. Use the provenance-required path for delivery artifacts; the fence does not distinguish external commits from member commits by itself.
- The package is not production-ready and has no real-user benchmark.
- There is no evidence yet that two teams / six active workers outperform a single agent on a controlled task set.

- Worktree reclaimer (`src/git/worktree-reclaim.mjs`): capacity is now advisory only. A checkout is removed only when every task referencing it is terminal, TTL-expired, has an artifact outside the checkout (or its kind never produces a commit), and git reports it clean. Blocked/conflict/rejected/review_stale/ff_exhausted/revert_failed/publication_unknown and unknown merge states are retained for diagnosis; `cancelled`/`failed` rows with the dispatch-time `pending` marker are treated as abandoned. Report counts `remaining` (surviving referenced directories) and `active` (protected or unsuccessfully cleaned) separately, and every filesystem removal is followed by a transactional task re-read so a concurrent reopen/re-dispatch cannot have its new worktree pointer cleared by a stale decision.

## Unreleased - bottom-layer hardening and scheduler module split (2026-11-04)

- Worktree fence: the lock is keyed by the physical worktree (realpath, Windows case-folded) instead of attempt/task, so two writers cannot lock the same directory twice; a half-written lock is treated as held for a five-second grace period. `expectCommit(inspected.head)` binds verification to the exact commit this attempt inspected, so a later external commit is rejected even when the tree is clean.
- Publication: `fastForwardBranch` now requires the current checkout to be the explicit target, a full expected commit that is an ancestor of the branch, an old target that is an ancestor of the new target, and a tracked-clean worktree; it compare-and-swaps `refs/heads/<target>` via `git update-ref <new> <old>`, then resets the checkout and reports `worktreeSynced`. The scheduler escalates `worktreeSynced:false` with `publicationWorktreeSync` and `merge.publication_worktree_not_synced` instead of reporting a clean merge.
- Discard: deleting an integration branch distinguishes a missing ref (idempotent success) from lock/permission/IO failures (propagated). A failed `reconcilePublication(applied:false)` keeps the guard and recovery record, returns `retryable:true` and emits `merge.publication_discard_failed`.

- A task that turns `failed` (a red box in the task tree) now automatically creates one review task with the dedicated kind `red-auto-review`, subject `自动继续审查`, `hidden: true`, and no assignee/attempt/lease. The review does exactly one thing: `agent_teams_continue_task` on the failed task, i.e. the literal message `继续` to the same task id and session. It never reads or reviews code, never creates an implementation task, and never edits the subject.
- Idempotency is structural: the review id is `redreview_<sha1(taskId + ':' + lastAttemptId)>`, so one failure event yields exactly one row through the direct failure hook, the `tick()` recovery sweep, concurrent ticks and a daemon restart. A review cancelled by `halt` is reopened under the same id after `resume`.
- The review runs asynchronously from the daemon (no worker slot, no model session, no blocking of the tick). A contractor with `purpose: 'red_auto_review'` can run it in its own slot instead, also without a model session; ordinary members and contractors without that purpose cannot (`403 E_FORBIDDEN`, `red_review.denied`).
- The counter is per task+session (`redContinueCount`/`redContinueSessionId`), reset by a successful turn, task completion, a session change or a manual continue. At `zcode.redAutoReview.maxContinues` (default 3) the next red box sends no `继续`, sends one urgent message to the captain with taskId, subject, count, sessionId and the last error, sets `redReviewEscalated` and stops until a human acts. Layering with the turn retry: 3 turn continues first, only then the review layer, which grants a fresh turn budget per continue.
- Review rows are hidden from `GET /teams/:id`, `GET /teams/:id/tasks`, the `/ui/snapshot` panel tree and `audit()`, and always finish `completed` with an `outcome`, so the tree never accumulates red review nodes. `GET /teams/:id` returns a `redReviews` summary instead; admins can read raw rows with `?includeHidden=1`.
- Added `zcode.redAutoReview` (`enabled`, `maxContinues`, `retryDelayMs`, `maxAttempts`) to config defaults, schema, validation and `config/README.md`; `isRetryableRedReviewError`, `redReviewKey`, `redReviewTaskId`, `redReviewEscalationText`, `RED_REVIEW_KIND`/`RED_REVIEW_ACTOR`/`RED_REVIEW_PURPOSE` domain helpers; events `red_review.*` and `task.red_escalated`.
- Tests: `test/red-auto-review.test.mjs` covers the automatic creation, idempotency across hook/sweep/restart, the continue-only action, the three-continue limit and captain message, the turn-retry layering, contractor execution versus plain-member denial, tree/API hiding and the `enabled=false` switch, plus a manual captain continue that restarts the cycle after an escalation, the per-session budget reset and the busy-member deferral/retry path.
